# План реализации MVP «Календарь звонков»

План по срезам к [SPEC.md](./SPEC.md). Каждый срез — самостоятельная задача, которую можно вести отдельной ветвью и мержить отдельным PR. После плана не должно остаться открытых продуктовых решений; всё, что не задано здесь, — деталь реализации внутри среза.

## Правила срезов

- **Порядок:** 1 → 2 → 3 → 4–5 (параллельно) → 6 → 7. Срез не начинается, пока не закрыты его зависимости.
- **Зелёный срез:** `npm run check` (без `TEST_DATABASE_URL` — интеграционные скипаются с предупреждением; с Docker — идут) и `npm run build` без секретов БД.
- **Никаких секретов в репозитории.** `DATABASE_URL`/`DIRECT_URL` — только локально и в Vercel/GitHub.
- **Одна конвенция тестов:** unit и компонентные рядом с модулем, интеграционные — `*.integration.test.ts`.
- **Запрещено:** `drizzle-kit push`, миграции из сборки Vercel, редактирование применённых миграций, правка `main` в обход PR.
- **Не входит в срезы:** редактирование/удаление типов, отмена записи, email-уведомления, несколько владельцев, авторизация, часовой пояс гостя, пагинация, OpenAPI и внешний API, Server Actions, e2e с `next start`.

## Срез 1. База данных, миграции, сиды

**Цель:** схема из SPEC §5 существует в виде миграций, применяется на Docker-базе, сиды идемпотентны, есть рантайм-клиент БД.

**Предусловие:** установлен Docker (OrbStack или Docker Desktop) — без него срез не проверяется.

**Работы**

- Зависимости с точными версиями: `drizzle-orm@0.45.4`, `pg@8.23.1`, `drizzle-kit@0.31.11` (dev), `@types/pg`.
- `drizzle.config.ts`: `DIRECT_URL`, `dialect: postgresql`, каталог `drizzle/`.
- `src/db/schema.ts`: таблицы `event_types`, `bookings` и все check-ограничения из SPEC §5.
- Миграции: `drizzle/0000_init.sql` из схемы и `drizzle/0001_bookings_no_overlap.sql` (`drizzle-kit generate --custom`) с EXCLUDE, check и b-tree индексом; обе коммитятся.
- `src/db/index.ts`: singleton `pg.Pool` (`max: 1`, `prepare: false`) на `DATABASE_URL`; ничего не создаётся на этапе импорта, сборка без переменной проходит.
- `src/db/seed.ts`: `call-15`/`call-30`, `ON CONFLICT (id) DO NOTHING`.
- `docker-compose.test.yml`: `postgres:17`, порт 5433, tmpfs, healthcheck.
- Скрипты: `db:generate`, `db:migrate`, `db:seed`, `db:test:up`, `db:test:down`.
- `.github/workflows/db-migrate.yml`: `workflow_dispatch`, Node 24, `npm ci`, `npm run db:migrate` (секрет репозитория `DIRECT_URL`), затем `npm run db:seed`.
- `.env.example`: `TEST_DATABASE_URL` с дефолтом Docker.
- README-раздел о миграциях и сидах можно оставить заготовкой — финальный текст в срезе 6.

**Готово, когда**

- [ ] `docker compose -f docker-compose.test.yml up -d` поднимает `postgres:17` на 5433 и healthcheck зелёный.
- [ ] `DIRECT_URL=postgres://postgres:postgres@localhost:5433/calendar_test npm run db:migrate` применяет обе миграции; повторный запуск — no-op.
- [ ] `npm run db:seed` дважды подряд не падает и не дублирует типы.
- [ ] `psql` подтверждает: пересечение даёт `23P01` с `constraint = 'bookings_no_overlap'`, встык проходит, `ends_at <= starts_at` и NULL-границы отклоняются, удаление типа с записью — `23503`.
- [ ] `npm run build` проходит без `DATABASE_URL`.
- [ ] Workflow `db-migrate.yml` проходит синтаксическую проверку и не вызывается из сборки.

**Зависимости:** нет.

## Срез 2. Тестовая инфраструктура и CI

**Цель:** unit/компонентные и интеграционные тесты разведены, интеграционные идут против настоящего Postgres, CI поднимает Postgres.

**Работы**

- `@vitest/coverage-v8`, совместимый с `vitest@5.1`.
- `vitest.config.mts`: исключить `**/*.integration.test.ts`; сбор покрытия в общий `reportsDirectory`.
- `vitest.integration.config.mts`: окружение `node`, `globalSetup`, `fileParallelism: false`.
- `src/test-utils/global-setup.ts`: программный `migrate()` на `TEST_DATABASE_URL`; без переменной — явное предупреждение и пропуск.
- `src/test-utils/fixtures.ts`: общие билдеры типов и записей.
- Скрипты: `test`, `test:run`, `test:integration`, `test:integration:run`, `test:coverage:run`; `check` = `format:check && typecheck && test:coverage:run`.
- Первый интеграционный тест `src/db/bookings-overlap.integration.test.ts`: конкурентный уровень 1 из SPEC §9.3 — два параллельных `insert ... on conflict do nothing`, ровно одна строка, второй получает `23P01`.
- Перенести 4 теста из `__tests__/` к страницам и компонентам (`src/app/page.test.tsx` и т. д.), удалить `__tests__/`.
- `.github/workflows/quality.yml`: service container `postgres:17` (5433, healthcheck), `TEST_DATABASE_URL`, шаг `npm run check`; `build` остаётся без БД.

**Готово, когда**

- [ ] `npm run test:run` не запускает интеграционные тесты.
- [ ] `npm run test:integration:run` с `TEST_DATABASE_URL` накатывает миграции и проходит конкурентный тест; второй прогон стабилен.
- [ ] Без `TEST_DATABASE_URL` интеграционный прогон скипается с понятным предупреждением и не валит `check`.
- [ ] CI `quality` зелёный с Postgres; без сервиса сборка (`build`) зелёная.
- [ ] `npm run check` зелёный локально в обоих режимах.

**Зависимости:** срез 1.

## Срез 3. Контракт, домен и роутер

**Цель:** все пять процедур работают через `createRouterClient` и `RPCHandler`, правила слотов и ошибки реализованы, UI ещё нет.

**Работы**

- Зависимости с точными версиями: `@orpc/contract@1.16.3`, `@orpc/server@1.16.3`, `@orpc/client@1.16.3`, `zod@4.6.7`.
- `src/lib/config`: профиль владельца и параметры сетки (SPEC §6.5).
- `src/contract/`: Zod-схемы из SPEC §6.2, `.route()` у каждой процедуры, `.errors()` с кодами из SPEC §6.3.
- `src/server/domain/slots.ts`: чистый `generateSlots` — окно 14 дней по Москве, 09:00–18:00, шаг по длительности, фильтр прошлого и пересечений.
- `src/server/router.ts`: `implement(contract)`; `eventTypes.create` с `EVENT_TYPE_EXISTS`; `availability.get` с `EVENT_TYPE_NOT_FOUND` и `no-store`; `bookings.create` с проверками слота, вычислением `endsAt`, вставкой `on conflict ... do nothing returning`, повтором на `40P01`, маппингом `23P01`/`40P01` → `SLOT_TAKEN` и `57014` → `SLOT_TIMEOUT`; `bookings.listUpcoming` с join-ом типа.
- `src/server/context.ts`: `{ db, now }`, `now` — функция, по умолчанию `() => new Date()`.
- `src/app/api/rpc/[[...rest]]/route.ts`: только `RPCHandler`, `prefix: '/api/rpc'`.
- `src/lib/orpc-client.ts`: `RPCLink` + `createORPCClient`, `ContractRouterClient`.
- Тесты: unit `generateSlots` и валидации; интеграционные по списку SPEC §9.3; конкурентный уровень 2; 2–3 контрактных теста через `RPCHandler.handle`.

**Готово, когда**

- [ ] Все пять процедур отвечают через `RPCHandler` по адресам из SPEC §6.2; `GET` без `.route({ method: 'GET' })` не остаётся.
- [ ] Unit-тесты покрывают границы сетки: 15/30 мин, 17:45/17:30, прошлые старты, полночь Москвы, 14 дней, блокировку пересекающихся стартов.
- [ ] Интеграционные тесты покрывают создание, дубль слота и типа, слот вне сетки/часов/прошлого, отсутствующий тип, `availability.get`, `listUpcoming`.
- [ ] Конкурентный тест процедуры: два соединения, ровно один успех и один `SLOT_TAKEN`.
- [ ] Контрактный тест подтверждает 400 с `data.issues` и 409 `SLOT_TAKEN` на HTTP-уровне.
- [ ] `npm run check` с Docker и `npm run build` без БД зелёные.

**Зависимости:** срезы 1–2.

## Срез 4. Экран `/booking`

**Цель:** гость проходит путь «тип → день → время → шторка → запись» по SPEC §7.1.

**Работы**

- `src/app/booking/page.tsx`: Server Component, `eventTypes.list` через `createRouterClient`; пустое состояние «Пока нет типов событий».
- Клиентские компоненты `/booking`: селект типа, панель типа, сетка 14 дней (2×7) со счётчиками, панель времени, шторка, состояния загрузки/пустоты/ошибки/успеха.
- Запрос `availability.get` из браузера; при загрузке — первый тип и первый день со слотами; смена типа сбрасывает день и слоты.
- Форма: валидация по SPEC §4.4 и §7.1, сохранение имени/email при закрытии, блокировка повторной отправки.
- Обработка `SLOT_TAKEN` (закрытие шторки, сброс слота, сохранение контактов, перезапрос дня, `role="alert"`, деактивация опустевшего дня), `SLOT_TIMEOUT`/500/сеть (шторка открыта), `EVENT_TYPE_NOT_FOUND`.
- Успех — «билет» с кнопками «Записаться ещё раз» и «На главную».
- Компонентные тесты: успешная запись и сценарий 409 (SPEC §9.3).

**Готово, когда**

- [ ] Сценарий из SPEC §7.1 проходится вручную на локальной базе: выбор типа, дня, времени, отправка, «билет».
- [ ] Пустые состояния: нет типов; нет слотов в окне; нет слотов у выбранного дня — совпадают с текстами спеки.
- [ ] 409 воспроизводится (занять слот параллельным запросом): шторка закрыта, контакты сохранены, день перезапрошен, сообщение с `role="alert"`.
- [ ] Двойной submit не создаёт вторую запись; кнопка блокируется, шторка не закрывается.
- [ ] Компонентные тесты успеха и 409 зелёные; `npm run check` и `npm run build` зелёные.
- [ ] Термин «Тип события» во всех новых текстах; ссылок на `/admin` на экране нет.

**Зависимости:** срез 3.

## Срез 5. Экран `/admin`

**Цель:** владелец создаёт типы событий и видит предстоящие записи по SPEC §7.2.

**Работы**

- `src/app/admin/page.tsx`: Server Component, `eventTypes.list` + `bookings.listUpcoming` через `createRouterClient`.
- Лента предстоящих записей: группировка по дням Москвы, сортировка по возрастанию, строка «время / имя / email / тип», счётчик в шапке.
- Список типов слева со счётчиками, «Все типы» по умолчанию, фильтр на клиенте.
- Модальное окно создания типа: слаг, название, описание, длительность (5–540, шаг 5); валидация, `EVENT_TYPE_EXISTS` под полем, общий текст на прочие сбои.
- После создания: модалка закрыта, тип в конце списка и подсвечен, фильтр переключён на него.
- Пустые состояния: нет типов, нет записей для «Все типы» и для конкретного типа.
- Компонентные тесты: фильтр и валидация формы создания типа.

**Готово, когда**

- [ ] Сценарий SPEC §7.2 проходится вручную: создание типа, появление в списке, фильтр, лента записей, созданных гостем.
- [ ] Дубль слага показывает «Такой слаг уже занят» под полем, модалка не закрывается.
- [ ] Границы длительности 4/5/540/545 и формат слага отклоняются с понятными ошибками.
- [ ] Пустые состояния совпадают с текстами спеки.
- [ ] Компонентные тесты зелёные; `npm run check` и `npm run build` зелёные.

**Зависимости:** срез 3 (можно параллельно со срезом 4).

## Срез 7. Деплой и прод-проверка

**Цель:** прод открыт гостям, миграции и сиды применены, запись работает, Supabase не засыпает.

**Работы**

- `vercel.json`: `schedules` для ежедневного пинга; приватная функция с `handleSchedule` (`@vercel/schedules`) и `select 1` через `DATABASE_URL`.
- GitHub: секрет репозитория `DIRECT_URL`; ручной запуск `db-migrate.yml` до мержа/деплоя, затем сид.
- Задеплоить `main`; проверить `/`, `/booking`, `/admin` без входа.
- Прод-сценарий: создать запись гостем, увидеть её в админке, проверить конфликт двух вкладок.
- Выполнить `pg_dump` после релиза, сохранить вне Supabase и GitHub; проверить инструкцию восстановления.
- Отметить в README фактический прод-URL и шаги эксплуатации.

**Готово, когда**

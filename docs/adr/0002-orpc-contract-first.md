# Контракт API — oRPC 1.16.3 contract-first, без OpenAPI-кодогена

**Статус:** accepted
**Дата:** 2026-11-19

Интерфейс между UI и сервером строится на **oRPC стабильной ветки `1.16.3`** (точный пин, без `^`): Zod-схемы в `src/contract/` — единственный источник правды, `implement(contract)` даёт роутер, `RPCHandler` монтируется в `/api/rpc/[[...rest]]`, Server Components вызывают `createRouterClient` в процессе, браузер — `RPCLink`. Доменные ошибки объявляются в контракте через `.errors()` и типизируются на клиенте. OpenAPI-файла, `openapi-typescript`/`openapi-fetch` и изолированного `tools/codegen` нет. Полный контракт и таблица ошибок — в резолюции [#14](https://github.com/Barrierok/frontend-project-386/issues/14).

## Рассмотренные альтернативы

- **Вариант A из `docs/research/contract-first-codegen.md`** (OpenAPI YAML → `openapi-typescript` → `openapi-fetch`): рекомендован исследованием по умолчанию, но потребитель у API один — собственный UI, а `openapi-typescript` не работает с TypeScript 7, поэтому требует изолированного `tools/codegen` на TS 5 и коммита сгенерированных типов. Церемония не окупается пятью эндпоинтами.
- **Вариант D** (Zod-схемы + `z.infer` + ручные `fetch`-обёртки): минимально, но пути и методы держит только код клиента, а типизированные ошибки и валидация ответа пишутся руками.
- **Server Actions**: удобны для форм без JS, но 409 пришлось бы кодировать в теле ответа, а клиентская логика (блокировка двойной отправки, перезапрос слотов после конфликта) и так требует явных вызовов.
- **`ts-rest`** отпал как неподдерживаемый (нет релизов с 2025, peer-зависимости Zod 3 и Next ≤ 14).

## Последствия

- **Документация.** `orpc.dev` описывает v2 (`2.0.0-beta`), к 1.16.3 неприменимую; источник правды для проекта — `https://v1.orpc.dev`. Обновление до 2.x — отдельная миграция, а не рутинный апдейт.
- **Ответственность валидации выходных схем.** oRPC проверяет `output` и на расхождении отдаёт 500 «Output validation failed» без деталей в теле; смена статуса возможна только middleware'ом, и мы сознательно этого не делаем.
- **`GET`-процедуры** обязаны иметь `.route({ method: 'GET' })`: при включённом по умолчанию `strictGetMethodPluginEnabled` иначе возвращается 405.
- **Контекст.** В 1.16.3 `RPCHandler` принимает `context` только объектом, поэтому `{ db, now }` собирается внутри обработчика на каждый запрос; функция-контекст появится в v2.
- **ESM-only.** Все пакеты `@orpc/*` поставляются только как ESM; для CJS-скриптов нужен Node 22+.
- **Задел на OpenAPI.** Метаданные `.route({ method, path })` уже стоят в контракте, поэтому `OpenAPIHandler` добавляется позже без правок схем и обработчиков.

# Непересечение записей гарантирует EXCLUDE-ограничение

**Статус:** accepted
**Дата:** 2026-11-18

В MVP записи гостей не пересекаются никогда, в том числе при одновременных запросах. Гарантию даёт декларативное `EXCLUDE USING gist (tstzrange(starts_at, ends_at) WITH &&)` на таблице `bookings`, а не SERIALIZABLE или advisory locks: ограничение проверяет сам Postgres при READ COMMITTED, его нельзя обойти другим путём записи, и оно не требует ретраев. Вставка идёт одной командой `insert ... on conflict on constraint bookings_no_overlap do nothing returning id`; 0 строк означает «слот занят» (409). Имя `bookings_no_overlap` — часть контракта: на него ссылается `on conflict`, его проверяют тесты, переименование ломает код.

## Рассмотренные альтернативы

- **SERIALIZABLE с ретраями** — сам по себе не гарантирует инвариант: нужен предварительный `SELECT`, а любой путь записи без него создаёт пересечение. Конфликты дают `40001` и лишние повторы.
- **Advisory lock** — держится только на дисциплине всех путей записи и огрубляет параллелизм; в transaction mode пулера допустим только `_xact_`-вариант.

## Последствия

- EXCLUDE не выражается в Drizzle-схеме: он живёт только в ручной SQL-миграции `0001_bookings_no_overlap.sql`. `drizzle-kit generate` его не видит, `drizzle-kit push` запрещён.
- `ON CONFLICT DO NOTHING` использует speculative insertion и обходит редкий `40P01`; запасной маппинг `40P01` → 409 после одного повтора всё равно нужен.
- `check (ends_at > starts_at)` и `NOT NULL` на границах обязательны: пустой или NULL-диапазон проходит мимо EXCLUDE.
- Ограничение глобальное (один календарь). Несколько владельцев потребуют `btree_gist` и колонку-скоуп, то есть новую миграцию, а не ослабление текущего ограничения.
- Подробности и замеры: `docs/research/postgres-no-overlap.md` на ветке `research/postgres-no-overlap`.

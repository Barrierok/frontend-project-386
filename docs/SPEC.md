**Статус:** собрана из решений карты [#7](https://github.com/Barrierok/frontend-project-386/issues/7), тикет [#16](https://github.com/Barrierok/frontend-project-386/issues/16).
**Дата:** 2026-11-19.
**Источники:** резолюции [#8](https://github.com/Barrierok/frontend-project-386/issues/8)–[#15](https://github.com/Barrierok/frontend-project-386/issues/15), [#17](https://github.com/Barrierok/frontend-project-386/issues/17), [ADR 0001](./adr/0001-booking-no-overlap.md), [ADR 0002](./adr/0002-orpc-contract-first.md), [GLOSSARY.md](../GLOSSARY.md).

План реализации по срезам — [PLAN.md](./PLAN.md).

## 1. Назначение и рамки

Сервис, в котором **владелец календаря** публикует **типы событий**, а **гости** занимают **слоты**. Продукт в интерфейсе называется **Calendar**. MVP — две роли без авторизации:

- **Владелец** создаёт типы событий и видит предстоящие записи всех типов одним списком. Владелец — один заранее заданный профиль; страница `/admin` открыта всем.
- **Гость** видит список типов событий, выбирает слот в окне 14 календарных дней и создаёт запись, оставив имя и email.

Один экземпляр календаря, одна часовая зона Europe/Moscow. Регистрации, входа и владельческих прав нет.

## 2. Роли и доступ

| Роль     | Что может                                                                 | Ограничения                                             |
| -------- | ------------------------------------------------------------------------- | ------------------------------------------------------- |
| Владелец | Создавать типы событий, видеть предстоящие записи, фильтровать их по типу | Нет редактирования и удаления типов, нет отмены записей |
| Гость    | Выбирать тип события, день и слот, создавать запись                       | Не видит чужие данные, кроме занятости слотов           |

- `/admin` не защищён: авторизации в MVP нет, глобальная навигация показывает ссылку «Админка» всем.
- На экране `/booking` ссылок на `/admin` нет.
- Профиль владельца — константа в `src/lib/config` (см. §6.5), а не запись в БД.

## 3. Домен

Термины — по [GLOSSARY.md](../GLOSSARY.md). В коде, UI и документации используется «**Тип события**», не «тип встречи».

| Термин             | Значение                                                               |
| ------------------ | ---------------------------------------------------------------------- |
| Тип события        | Шаблон: слаг-идентификатор, название, описание, длительность в минутах |
| Слот               | Конкретный интервал, который гость может занять в рамках типа          |
| Окно записи        | 14 календарных дней, начиная с сегодняшнего (Europe/Moscow)            |
| Запись             | Занятый слот с именем и email гостя                                    |
| Предстоящая запись | Запись, начало которой ещё не наступило (`starts_at > now`)            |

## 4. Правила бронирования

### 4.1 Окно, рабочие часы, сетка

- Время — одна зона **Europe/Moscow** (UTC+3, без перехода на летнее время), без пересчёта для гостя.
- Окно записи — **14 календарных дней**, начиная с сегодняшнего по Москве. Дни — `[today, today + 13]`; полночь считается по Москве, не по UTC.
- Рабочие часы — **09:00–18:00**, все 7 дней недели.
- Шаг стартов равен длительности выбранного типа: старты идут от 09:00 с этим шагом, последний старт — такой, что `старт + длительность <= 18:00` (30 мин → 17:30, 15 мин → 17:45).
- Старт строго в будущем: в сегодняшнем дне прошедшие и текущий моменты скрыты. Условие записи — `startsAt > now`.
- Тип длительностью 540 минут даёт ровно один старт — 09:00; более длинных типов нет.
- Сетка одна на все типы: занятость общая, запись любого типа блокирует пересекающиеся старты любого другого типа.

### 4.2 Свободные слоты

Слот свободен, если его интервал `[startsAt, startsAt + duration)` не пересекается ни с одной существующей записью. Проверка идёт по всей таблице `bookings`, глобально, без фильтра по типу события.

`availability.get` возвращает все 14 дней окна, включая дни с нулём слотов, и слоты по возрастанию старта.

### 4.3 Непересечение записей

- Записи не пересекаются **никогда**, в том числе при одновременных запросах.
- Гарантия — декларативное ограничение `EXCLUDE USING gist (tstzrange(starts_at, ends_at) WITH &&)` с именем `bookings_no_overlap` ([ADR 0001](./adr/0001-booking-no-overlap.md)). Прикладная проверка перед вставкой защитой не является.
- Вставка — одной командой `insert ... on conflict on constraint bookings_no_overlap do nothing returning ...`. Ноль строк означает «слот занят» → ошибка `SLOT_TAKEN`, HTTP 409.
- SQLSTATE `23P01` (`exclusion_violation`) и `40P01` (deadlock) маппятся в `SLOT_TAKEN`; для `40P01` допускается один повтор вставки.
- Внешних вызовов внутри транзакции вставки нет; `SET LOCAL statement_timeout = '5s'`; `57014` → `SLOT_TIMEOUT`, HTTP 503.
- Границы полуоткрытые: `[starts_at, ends_at)`, поэтому записи «встык» допустимы. `check (ends_at > starts_at)` и `NOT NULL` на границах обязательны.
- Ограничение глобальное: несколько владельцев потребуют `btree_gist` и колонку-скоуп, то есть новую миграцию.

### 4.4 Валидация входа

Сервер — единственный авторитет; клиентская валидация повторяет те же правила и тексты.

| Поле             | Правило                                                                          |
| ---------------- | -------------------------------------------------------------------------------- |
| Слаг типа (`id`) | 1–64 символа, `^[a-z0-9]+(-[a-z0-9]+)*$`, редактируется вручную                  |
| Название типа    | trim, 1–100 символов                                                             |
| Описание типа    | необязательное, до 500 символов; по умолчанию `""`; пустое не рендерится у гостя |
| Длительность     | целое 5–540, кратно 5                                                            |
| Имя гостя        | trim, 1–100 символов                                                             |
| Email гостя      | trim + нижний регистр, 3–254, формат `z.email()`                                 |

Тексты ошибок полей: «Укажите имя», «Введите корректный email». Занятый слаг: «Такой слаг уже занят». Прочий сбой сохранения типа: «Не удалось сохранить, попробуйте ещё раз».

Гость присылает только `eventTypeId`, `startsAt`, `guestName`, `guestEmail`. `endsAt` и длительность вычисляет сервер из типа события.

## 5. Модель данных

Две таблицы. Владельца, статусов, soft delete и снимка названия/длительности в записи нет.

```sql
create table event_types (
  id text primary key,
  title text not null,
  description text not null default '',
  duration_minutes integer not null,
  created_at timestamptz not null default now(),

  constraint event_types_id_format
    check (id ~ '^[a-z0-9]+(-[a-z0-9]+)*$'),
  constraint event_types_id_length
    check (char_length(id) between 1 and 64),
  constraint event_types_title_length
    check (char_length(btrim(title)) between 1 and 100),
  constraint event_types_description_length
    check (char_length(description) <= 500),
  constraint event_types_duration_range
    check (duration_minutes between 5 and 540 and duration_minutes % 5 = 0)
);

create table bookings (
  id uuid primary key default gen_random_uuid(),
  event_type_id text not null
    references event_types (id) on delete restrict,
  starts_at timestamptz not null,
  ends_at timestamptz not null,
  guest_name text not null,
  guest_email text not null,
  created_at timestamptz not null default now(),

  constraint bookings_time_valid
    check (ends_at > starts_at),
  constraint bookings_guest_name_length
    check (char_length(btrim(guest_name)) between 1 and 100),
  constraint bookings_guest_email_length
    check (char_length(btrim(guest_email)) between 3 and 254),
  constraint bookings_no_overlap
    exclude using gist (tstzrange(starts_at, ends_at) with &&)
);

create index bookings_starts_at_idx on bookings (starts_at);
```

- `ends_at` вычисляется сервером при вставке и фиксируется; в `bookings` длительность не дублируется.
- Индекс по `event_type_id` не нужен: занятость читается глобально по диапазону, лента сортируется по `starts_at`, join идёт по PK.
- В БД только структурные инварианты. Рабочие часы, окно, шаг, совпадение длительности, формат email и чтение занятости — вычисления и валидация сервера, без триггеров.
- `EXCLUDE` не выражается в Drizzle-схеме: он живёт только в ручной SQL-миграции. `drizzle-kit push` запрещён.

Сиды (идемпотентно):

```sql
insert into event_types (id, title, description, duration_minutes) values
  ('call-15', 'Звонок на 15 минут', 'Короткий звонок, чтобы обсудить один вопрос.', 15),
  ('call-30', 'Звонок на 30 минут', 'Развёрнутый разговор по задаче или консультация.', 30)
on conflict (id) do nothing;
```

## 6. Серверный контракт

### 6.1 Транспорт и раскладка

**oRPC 1.16.3 contract-first**, точный пин без `^`; документация — `https://v1.orpc.dev` ([ADR 0002](./adr/0002-orpc-contract-first.md)). Zod-схемы — единственный источник правды. OpenAPI-файла и кодогена нет.

```
src/contract/            # oc-контракт: схемы, .errors(), .route()
src/server/router.ts     # implement(contract), обработчики
src/server/context.ts    # тип и сборка { db, now }
src/server/domain/       # generateSlots и прочие чистые правила
src/app/api/rpc/[[...rest]]/route.ts
src/lib/orpc-client.ts   # браузерный клиент
```

- Монтируется только `RPCHandler` из `@orpc/server/fetch` с `prefix: '/api/rpc'`; `OpenAPIHandler`, Server Actions, TanStack Query и генераторы хуков не используются.
- У каждой процедуры стоит `.route({ method, path })`; у `GET`-процедур `method: 'GET'` обязателен (`strictGetMethodPluginEnabled`, иначе 405).
- Server Components вызывают `createRouterClient(router, { context })` — в процессе, без HTTP. Браузер — `RPCLink` из `@orpc/client/fetch` + `createORPCClient`, тип `ContractRouterClient<typeof contract>`.
- `context = { db, now }`: `db` — Drizzle-клиент из singleton-пула, `now` — функция текущего момента, подменяемая в тестах. В 1.16.3 `RPCHandler` принимает контекст только объектом, поэтому он собирается в обработчике на каждый запрос.
- Все пакеты `@orpc/*` — ESM-only; нужен Node 22+.

### 6.2 Процедуры и схемы

| Процедура               | HTTP-метаданные                      | Вход              | Выход                  |
| ----------------------- | ------------------------------------ | ----------------- | ---------------------- |
| `eventTypes.list`       | `GET /event-types`                   | —                 | `EventType[]`          |
| `eventTypes.create`     | `POST /event-types`                  | `EventTypeInput`  | `EventType`            |
| `availability.get`      | `GET /event-types/{id}/availability` | `{ eventTypeId }` | `{ days: DaySlots[] }` |
| `bookings.create`       | `POST /bookings`                     | `BookingInput`    | `Booking`              |
| `bookings.listUpcoming` | `GET /bookings/upcoming`             | —                 | `Booking[]`            |

```ts
EventType      { id, title, description, durationMinutes, createdAt }
EventTypeInput { id, title, description?, durationMinutes }   // description по умолчанию ""
Booking        { id, startsAt, endsAt, guestName, guestEmail, createdAt,
                 eventType: { id, title, durationMinutes } }
BookingInput   { eventTypeId, startsAt, guestName, guestEmail }
DaySlots       { date: "2026-11-19", slots: [{ startsAt }] }
```

- `eventTypes.list` — сортировка по `created_at` возрастанию, при равенстве по `id`.
- `eventTypes.create` — обрезает `title`, дефолт `description = ""`; конфликт PK → `EVENT_TYPE_EXISTS`.
- `availability.get` — только `{ eventTypeId }`; окно и сетка всегда 14 дней от «сегодня» по Europe/Moscow, считаются сервером; произвольные `from`/`days` не принимаются; ответ `no-store`.
- `bookings.create` — проверяет существование типа, слот в окне, внутри 09:00–18:00, `endsAt <= 18:00`, выравнивание по шагу длительности, `startsAt > now`; вычисляет `endsAt`; вставляет; возвращает созданную запись с join-ом типа.
- `bookings.listUpcoming` — `starts_at > now`, сортировка по возрастанию, тип join-ом. Пагинации и `LIMIT` нет; фильтр по типу — на клиенте.
- Валидация `output` включена: расхождение ответа со схемой — 500 (`Output validation failed`), детали только в логах.

### 6.3 Ошибки

Доменные ошибки объявлены через `.errors()` и типизированы на клиенте (`isDefinedError`, `e.code`, `e.data`). UI ветвится по `code` и показывает `message`.

| Код                     | HTTP | Сообщение                                            | Когда                                                       |
| ----------------------- | ---- | ---------------------------------------------------- | ----------------------------------------------------------- |
| `SLOT_TAKEN`            | 409  | «Это время уже занято, выберите другой слот»         | вставка вернула 0 строк, `23P01` или `40P01` после повтора  |
| `SLOT_UNAVAILABLE`      | 409  | «Слот недоступен, обновите страницу»                 | слот вне окна, вне рабочих часов, не по сетке или в прошлом |
| `SLOT_TIMEOUT`          | 503  | «Сервис перегружен, попробуйте ещё раз»              | `57014` (statement timeout)                                 |
| `EVENT_TYPE_EXISTS`     | 409  | «Тип события с таким идентификатором уже существует» | конфликт PK при создании типа                               |
| `EVENT_TYPE_NOT_FOUND`  | 404  | «Тип события не найден»                              | нет типа в `availability.get` / `bookings.create`           |
| `BAD_REQUEST`           | 400  | встроенное, `data.issues`                            | невалидный вход                                             |
| `INTERNAL_SERVER_ERROR` | 500  | встроенное                                           | непойманное исключение, провал валидации выхода             |

`SLOT_TIMEOUT` добавлен при сведении: решение #8 требует отличать `57014` от 409, а таблица #14 не задавала для него код.

### 6.4 Время

- API передаёт моменты в ISO 8601 UTC с `Z`; в БД — `timestamptz`.
- Сетка, рабочие часы, окно и группировка по дням считаются на сервере в Europe/Moscow.
- UI показывает московское время без пересчёта для гостя; форматирование — через `Intl.DateTimeFormat` с `timeZone: "Europe/Moscow"`.

### 6.5 Конфигурация

`src/lib/config` хранит:

- профиль владельца (`name`, `email`) — контент для шапки `/admin` и метаданных; на правила бронирования не влияет;
- параметры сетки: `timeZone: "Europe/Moscow"`, `windowDays: 14`, `workdayStartHour: 9`, `workdayEndHour: 18`.

Шаг сетки — не константа: он равен длительности выбранного типа события.

## 7. Экраны

### 7.1 `/booking` — запись гостя

Компоновка — вариант C прототипа ([#12](https://github.com/Barrierok/frontend-project-386/issues/12)): календарная сетка 14 дней, время панелью, форма в модальной шторке.

**Загрузка и шапка**

- Server Component загружает `eventTypes.list`; если типов нет — календаря нет, карточка «Пока нет типов событий» с пояснением, что владелец ещё ничего не добавил.
- Иначе сверху селект типа события (порядок `created_at` возрастанию, новые снизу). Под ним панель выбранного типа: название, длительность, описание (пустое не рендерится).
- При загрузке выбирается первый тип, у него запрашивается `availability.get`.

**Календарь**

- Сетка 14 дней двумя рядами по 7; у каждого дня счётчик свободных мест. Дни без слотов видны, но недоступны для клика, счётчик показывает «нет».
- При загрузке активен первый день со свободными слотами.
- Окно без единого слота: календарь остаётся (все дни «нет»), над ним баннер «Свободных слотов в ближайшие 14 дней нет» и подсказка выбрать другой тип, если он есть.

**Время**

- Панель под календарём: кнопки стартов выбранного дня по возрастанию.
- У дня без слотов — «В этот день свободных слотов нет».

**Шторка**

- Клик по времени открывает шторку: название типа, дата, время, длительность, «Имя», «Email», кнопка «Подтвердить запись».
- Закрытие (крестик, Escape, клик по фону) не теряет имя и email.
- Смена типа сбрасывает выбранный день, закрывает шторку и заново запрашивает слоты. Имя и email сохраняются до успешной записи или ухода со страницы.

**Валидация формы**

- Проверка по submit: ошибки под полями, фокус в первое невалидное, шторка не закрывается. После первой неудачной попытки поле перепроверяется на ввод.
- Тексты — «Укажите имя», «Введите корректный email»; правила — §4.4.
- Пока запрос в полёте, кнопка заблокирована и показывает загрузку, повторный submit игнорируется, шторку нельзя закрыть (крестик, Escape, фон). Серверной идемпотентности нет: второй запрос упрётся в `EXCLUDE` и получит 409, первый уже запишет гостя.

**409 `SLOT_TAKEN`**

Один сценарий для гонки и для занятого слота:

1. шторка закрывается, выбранный слот сбрасывается;
2. имя и email сохраняются;
3. слоты выбранного дня перезапрашиваются;
4. над календарём появляется сообщение «Это время уже занято, выберите другой слот» с `role="alert"`;
5. выбранный день остаётся активным; если после перезапроса слотов не осталось — день становится недоступным, панель показывает «В этот день свободных слотов нет».

**Прочие ошибки**

- `SLOT_TIMEOUT`, `INTERNAL_SERVER_ERROR`, сеть: шторка остаётся открытой, контакты сохранены, над кнопкой сообщение с `role="alert"` — для 503 текст из контракта, иначе «Не удалось создать запись, попробуйте ещё раз».
- `EVENT_TYPE_NOT_FOUND`: сообщение и перезагрузка списка типов.

**Успех**

Экран-«билет» на месте содержимого `/booking`: дата, время, длительность и название типа, обращение по имени, текст о том, что владелец увидит запись. Кнопки «Записаться ещё раз» (тот же тип, свежие слоты, пустая форма) и «На главную» (`/`). Письмо не отправляется и экран его не обещает.

### 7.2 `/admin` — кабинет владельца

Компоновка — вариант C прототипа: типы событий списком слева и фильтруют ленту, записи справа по дням, создание типа — в модальном окне.

**Лента**

- Предстоящая запись — `starts_at` строго в будущем относительно момента запроса.
- Сортировка по `starts_at` возрастанию, группировка по календарным дням Москвы с заголовком дня.
- Строка: время, имя, email, название типа.
- В шапке ленты — счётчик записей.
- Пагинации нет: окно записи 14 дней, прошедшее выпадает, объём ограничен сверху.

**Фильтр**

- Слева список типов со счётчиками, по умолчанию «Все типы»; порядок типов тот же, что у гостя.
- Фильтр применяется на клиенте.

**Пустые состояния**

- Нет типов — «Пока ни одного типа события».
- Нет записей — «Записей пока нет», с разным текстом для «Все типы» и конкретного типа.

**Создание типа события**

- Поля: слаг (`id`, редактируется вручную), название, описание, длительность — числовое поле 5–540 с шагом 5.
- Проверка по §4.4; занятый слаг — ошибка под полем «Такой слаг уже занят», не технический сбой.
- Прочие сбои — «Не удалось сохранить, попробуйте ещё раз».
- После создания модалка закрывается, тип появляется в конце списка слева и подсвечивается, фильтр переключается на него; у гостя тип виден при следующей загрузке страницы.

### 7.3 Общее

- Терминология интерфейса — «Тип события», «Слот», «Запись».
- Время везде московское, без переключателя зоны.
- Ссылка «Админка» есть в глобальной навигации; на `/booking` собственных ссылок на `/admin` нет.
- Пустые состояния, ошибки и загрузка доступны с клавиатуры и скринридеру; сообщения об ошибках — `role="alert"`.

## 8. Окружение и эксплуатация

### 8.1 Хранение и деплой

- **Supabase Free**, регион `eu-west-1`, PostgreSQL 17.12. Локальная разработка и прод смотрят в одну базу.
- **Vercel**, регион функций `dub1` (рядом с БД) через `vercel.json`. Vercel Authentication должна быть выключена: гости заходят без входа.
- Сборка и CI проходят без секретов БД.

### 8.2 Переменные

| Переменная                                | Локально                              | GitHub Actions            | Vercel            |
| ----------------------------------------- | ------------------------------------- | ------------------------- | ----------------- |
| `DATABASE_URL` (transaction pooler, 6543) | `.env.local`                          | не нужна (тесты — Docker) | Secret, все среды |
| `DIRECT_URL` (session pooler, 5432)       | `.env.local`, только `psql`/`pg_dump` | Secret репозитория        | нет               |
| `TEST_DATABASE_URL` (Docker, 5433)        | `.env.local` / env команды            | задаётся в job            | нет               |

- Рантайм: `pg` Pool `max: 1`, singleton на процесс, `prepare: false` (transaction pooler не поддерживает prepared statements).
- `DIRECT_URL` читают только `drizzle.config.ts` и скрипты `db:*`; в клиентский бандл он попасть не может.
- `.env.example` перечисляет все три переменные.

### 8.3 Миграции и сиды

- Единственный путь изменения схемы Supabase — workflow `.github/workflows/db-migrate.yml` с триггером `workflow_dispatch`: checkout → Node 24 → `npm ci` → `npm run db:migrate` (`drizzle-kit migrate`, `DIRECT_URL`) → `npm run db:seed`.
- Локального применения миграций к Supabase нет. Против Docker-базы миграции накатываются тем же `migrate()` в тестах.
- Авторский цикл: `drizzle-kit generate` (EXCLUDE — `generate --custom`) → проверка на Docker (`npm run test:integration`) → PR → ручной запуск workflow → мерж.
- Порядок — миграция до мержа, Vercel автодеплоит `main`. Только аддитивные миграции (expand/contract); применённые файлы не редактируются.
- Мигратор запускается только вручную: он не ставит блокировок и применяет всё одной транзакцией; вызов из сборки Vercel запрещён.
- Сид `src/db/seed.ts` + `npm run db:seed`: `call-15`/`call-30`, `ON CONFLICT (id) DO NOTHING`, идемпотентно; в проде шагом после миграции. Тесты сиды не используют.

### 8.4 Откат, бэкапы, пауза

- Forward-only: down-миграций нет, ошибка исправляется новой миграцией вперёд; упавшая миграция откатывается транзакцией.
- Supabase Free не делает автобэкапов и не поддерживает PITR. Владелец делает ручной `pg_dump` перед разрушительной миграцией и после каждого релиза, хранит вне Supabase и GitHub (репозиторий публичный; дамп с именами и email гостей в артефакты Actions не попадает).
- Восстановление из дампа и аварийное снятие паузы Supabase описаны в README.
- Пауза после ~7 дней низкой активности предотвращается ежедневным пингом: приватная функция по расписанию Vercel Schedules (`@vercel/schedules` + `handleSchedule`), `select 1` через рантайм-`DATABASE_URL`; расписание `0 6 * * *` UTC (09:00 МСК), джиттер на Hobby до 15 минут. Публичного `/api/health` нет.

## 9. Тестирование

### 9.1 Где живёт Postgres

- Локально — Docker `postgres:17`, `docker-compose.test.yml`: порт 5433, tmpfs, healthcheck; скрипты `db:test:up` / `db:test:down`.
- В CI — service container `postgres:17` в `quality.yml`.
- Один и тот же код, различается только `TEST_DATABASE_URL`; дефолт — `postgres://postgres:postgres@localhost:5433/calendar_test`.
- Тесты не ходят в боевую базу; отдельный тестовый проект Supabase не заводится.

### 9.2 Изоляция и швы

- Миграции — программный `migrate()` в `globalSetup` интеграционного конфига.
- Интеграционные тесты последовательны (`fileParallelism: false`); перед каждым — `TRUNCATE bookings, event_types RESTART IDENTITY CASCADE`.
- Основной шов — `createRouterClient` с реальным `db` и инжектированным `now`.
- 2–3 контрактных теста через `RPCHandler.handle(new Request(...))`: 400 от Zod и 409 `SLOT_TAKEN` — проверка HTTP-маппинга без запуска Next.
- Полного e2e с `next start` нет. Компонентные тесты мокают oRPC-клиент на границе хуков.

### 9.3 Обязательные тесты

Unit, без БД:

- `generateSlots`: шаг равен длительности; последний старт не выходит за 18:00; прошедшие старты скрыты; занятая запись блокирует все пересекающиеся старты; окно ровно 14 календарных дней; полночь по Москве, не по UTC.
- Валидация: длительность 5–540 кратно 5 (границы 4/5/540/545), формат слага, обязательность полей.

Интеграционные, настоящий Postgres:

- создание записи на свободный слот;
- повторное бронирование того же слота → `SLOT_TAKEN`;
- бронирование вне шага, вне рабочих часов или в прошлом → `SLOT_UNAVAILABLE`;
- `availability.get` исключает занятые слоты и возвращает все 14 дней;
- создание типа; дубль слага → `EVENT_TYPE_EXISTS`;
- запись с несуществующим типом → `EVENT_TYPE_NOT_FOUND`;
- `bookings.listUpcoming`: только будущие, по возрастанию.

Конкурентность, два уровня:

1. Ограничение: два параллельных `insert ... on conflict do nothing` по одному интервалу — ровно одна строка, второй получает `23P01`.
2. Процедура: два параллельных `bookings.create` через два соединения — ровно один успех и один `SLOT_TAKEN`.

Компонентные:

- успешная запись: день → панель времени → шторка → отправка → «билет»;
- 409: шторка закрыта, имя и email сохранены, слоты дня перезапрошены, сообщение с `role="alert"`;
- админка: фильтр по типу и валидация формы создания типа.

### 9.4 Структура, команды, покрытие

- Unit и компонентные — `*.test.ts(x)` рядом с модулем; интеграционные — `*.integration.test.ts` рядом с серверным кодом; фикстуры — `src/test-utils/fixtures.ts`; снапшотов нет.
- Существующие тесты из `__tests__/` переезжают к страницам; одна конвенция на репозиторий.
- Скрипты: `test` / `test:run` (unit + компонентные), `test:integration`, `test:integration:run`, `test:coverage:run` (оба проекта, один отчёт).
- `check` = `format:check && typecheck && test:coverage:run` — интеграционные входят в него.
- Без `TEST_DATABASE_URL` интеграционный прогон скипается с явным предупреждением: покрытие печатается, но порог не гейтит. В CI есть Postgres и `TEST_DATABASE_URL`, порог гейтит.
- Покрытие — 80% глобально по `statements`, `lines`, `functions`, `branches`; исключения: `src/components/ui/**`, `src/app/layout.tsx`, `src/app/globals.css`, `drizzle/**` и миграции, конфиг-константы, `src/test-utils/**`, `vitest.*`, `next.config.*`, `**/*.d.ts`.

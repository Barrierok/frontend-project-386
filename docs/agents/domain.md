# Документация домена

Как инженерные навыки должны использовать документацию домена этого репозитория при изучении кодовой базы.

## Перед изучением прочитай

- **`GLOSSARY.md`** в корне репозитория, либо
- **`GLOSSARY-MAP.md`** в корне, если он есть: он указывает на отдельный `GLOSSARY.md` для каждого контекста. Читай те, что относятся к теме.
- **`docs/adr/`**: читай ADR, затрагивающие область, в которой собираешься работать. В репозиториях с несколькими контекстами также проверяй `src/<context>/docs/adr/` на решения уровня контекста.

Если каких-то из этих файлов нет, **продолжай молча**. Не подчёркивай их отсутствие и не предлагай создать их заранее. Навык `/domain-modeling` (доступен через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно появляются.

## Структура файлов

Один контекст (большинство репозиториев):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Несколько контекстов (признак — `GLOSSARY-MAP.md` в корне):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← решения уровня системы
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения уровня контекста
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используй словарь глоссария

Когда в результате работы появляется доменное понятие (в заголовке задачи, предложении по рефакторингу, гипотезе, названии теста), используй термин в том виде, как он определён в `GLOSSARY.md`. Не уходи к синонимам, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо ты придумываешь язык, которого в проекте нет (подумай ещё раз), либо это реальный пробел (зафиксируй его для `/domain-modeling`).
